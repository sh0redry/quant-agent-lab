```markdown
# FinAutoRubric 评测与研究计划

## 1. 项目目标

响应导师“利用这个 benchmark 评测并改进 Agent”的建议：

1. 确认 FinAutoRubric 的资源和运行条件。
2. 建立一个现有金融研究 Agent 的基线。
3. 根据执行轨迹定位主要失败原因。
4. 选择一个与信息获取、理解或核验相关的问题进行改进。
5. 在相同条件下比较效果、成本与稳定性。

最终回答：

> 现有 Agent 在金融研究任务中主要失败在哪里？
> 我们提出的一个改进，能否在相同资源条件下减少这些失败？

最终交付：SUMMARY.md。
原始配置、运行记录和案例作为该文件的支撑证据。

## 2. 工作范围

近期优先：
- 固定题目和固定评分规则下的 Agent 评测。
- 证据获取、文档理解、时间与财务口径核验。
- 小规模、可复查的对照实验。

暂不作为必须完成项：
- 完整重建 FinAutoRubric 的 rubric 生成系统。
- 更换或训练基础模型。
- 强化学习训练。
- 交易收益、高频执行或世界模型实验。
- 在资源与协议未对齐前宣称官方复现或 SOTA。

## 3. 当前状态

以下均为待开展或待核验事项，不代表已经完成。

- [ ] 完成论文与评价协议整理
- [ ] 确认官方数据、rubric 和代码入口
- [ ] 跑通小规模评测
- [ ] 建立基线
- [ ] 完成失败分析
- [ ] 确定并冻结一个改进方案
- [ ] 完成独立评测与复核
- [ ] 完成 SUMMARY.md

## 4. 阶段一：资源与协议核验

### 4.1 检查资源

逐项记录来源链接、版本、检查日期和获取状态：

- 官方题目与题目 ID。
- 逐题评分规则及权重。
- 题目对应的信息截止时间。
- 官方评分代码和裁判提示词。
- Agent 运行框架与工具定义。
- 模型、推理设置、预算及终止规则。
- 示例答案、执行轨迹与结果。
- 数据及代码的使用许可。

状态统一使用：
- 已取得
- 仅论文描述
- 待核验
- 不可获得

不能将“论文称将发布”记为“已经取得”。

### 4.2 明确评价协议

开始模型调用前固定：

- 使用什么题目和版本。
- Agent 能访问哪些文件、网页和数据服务。
- 哪些时间之后的信息禁止使用。
- 可以调用哪些工具。
- step、工具调用和重试如何计数。
- 每题的步骤、时间、token 和费用上限。
- 如何处理超时、工具失败和未完成答案。
- 裁判看到最终答案，还是完整执行轨迹。
- 分数如何聚合。

没有查清的设置标记为未知，不自行冒充官方设置。

### 4.3 决策门槛

路径 A：核心资源齐全
- 开始官方题目上的试跑。
- 如有自行实现的组件，记录与原协议的差异。

路径 B：缺少官方题目或 rubric
- 列出缺失项，向导师汇报或索取资源。
- 使用 FinanceBench、FinQA 等公开资源验证运行流程。
- 替代实验使用独立名称和各自评价协议。
- 不称为 FinAutoRubric 官方复现。

本阶段完成条件：
能明确说出“现在能跑什么、不能跑什么、原因是什么”。

## 5. 阶段二：建立最小运行流程

### 5.1 选择起点

- 选择一个可用基础模型。
- 选择一个现有工具型 Agent 框架。
- 固定搜索、文件读取和计算工具。
- 第一轮不同时改模型、框架和检索方法。

配置示例中不放 API 密钥。

### 5.2 用 3—5 题检查流程

这些题作为开发材料，不进入后续独立评价集合。

每题执行：
1. 读取问题、信息截止时间和任务约束。
2. 允许 Agent 检索、读取与计算。
3. 生成最终答案。
4. 独立评价程序读取固定 rubric 并评分。
5. 保存日志与成本。
6. 人工检查记录是否完整。

答题 Agent 不得读取：
- 标准答案。
- 逐题评分中的预期值。
- 其他系统在该题的答案。
- 评价程序的私有文件。

### 5.3 最少保存的信息

- 题目 ID、数据版本和运行 ID。
- 模型版本、参数、提示词与配置版本。
- 每次工具调用及返回内容。
- 来源链接、文件名、页码和可确认的发布时间。
- 计算代码、输入和执行结果。
- 最终答案。
- 逐项评分及评分依据。
- 耗时、token、调用次数和费用。
- 工具错误、重试与终止原因。

本阶段完成条件：
至少一题可以从输入追查到评分，并能解释成本和失败原因。

## 6. 阶段三：建立基线

### 6.1 预先划分题目

在观察模型成绩前确定题目集合。

建议的小规模安排：
- 流程检查：3—5 题。
- 开发与错误诊断：约 10 题。
- 独立评价：约 20 题。

数量可随资源调整，但必须记录实际数量。
同一题及高度相似题不要跨开发与评价集合。

如果资源不足以划分：
只报告探索性诊断，不报告独立泛化结论。

### 6.2 基线配置

B0：普通检索＋回答
- 固定检索后生成答案。
- 作为简单参考，资源不足时可省略。

B1：现有工具型 Agent
- 自主搜索、读取和计算。
- 作为后续改进的主要比较对象。

先运行 B1，再决定是否需要 B0。

### 6.3 统计结果

记录：
- 总体分数与各类任务分数。
- 完成率与失败数量。
- 平均及高耗时题目的成本。
- 证据、口径、计算及论证错误。
- 工具故障和预算耗尽。

固定评价集合后，不因表现差而删题。
工具失败应保留并单独统计；重试规则预先约定。

本阶段完成条件：
取得一组有完整轨迹、可人工复查的基线结果。

## 7. 阶段四：失败分析

### 7.1 分类体系

每个失败案例记录一个主要原因，可附多个次要原因：

E1 信息获取：
必要证据没有进入 Agent 的上下文。

E2 文档解析：
表格、脚注、图表或页面内容读取错误。

E3 时间与口径：
年份、版本、单位、指标定义或合并范围混淆。

E4 计算：
输入正确，但公式、运算或程序执行错误。

E5 论证：
证据不足、忽略反证，或结论超出证据支持范围。

E6 运行：
工具错误、超时、预算耗尽或未完成。

E7 评价争议：
rubric、参考值或裁判判断可能存在问题。

### 7.2 归因方法

- 不只依据最终答案或裁判解释分类。
- 对照原始来源、检索结果和计算轨迹。
- 无法判定时标记“原因未确定”。
- 将评分争议与 Agent 错误分开。

必要时做诊断性干预：
- 补入正确证据后重跑。
- 提供正确数字后检查计算。
- 明确口径后检查答案是否改变。

这些属于辅助诊断，不计入正式端到端成绩。
一次干预成功也不能证明它是唯一失败原因。

### 7.3 本阶段产出

- 各类错误的题目数量与比例。
- 3—5 个完整案例。
- 一个最值得优先解决的问题。

选择问题时考虑：
- 出现频率。
- 对答案质量的影响。
- 是否存在明确改进机制。
- 数据和验证成本。
- 是否已有充分研究，需要避免重复。

## 8. 阶段五：验证一个改进

### 8.1 定义假设

根据错误分析填写：

主要错误：
__________

拟增加机制：
__________

预期影响：
__________

什么结果会否定该假设：
__________

可选机制包括：
- 主动补齐缺失证据。
- 时间、单位和财务口径核验。
- 发现矛盾后重新检索。
- 关键计算独立复核。

第一轮只选择一个主要机制。

### 8.2 构建 B2

B2 = B1 + 选定改进。

保持一致：
- 基础模型与推理设置。
- 数据权限和工具。
- 题目集合。
- 预算上限。
- 评分规则和裁判设置。

新增检查、审核或 Agent 的调用全部计入成本。

### 8.3 冻结后评价

- 在开发集合上调整方案。
- 冻结提示词、配置和代码。
- 再运行独立评价集合。
- 不根据独立评价中的具体错误反复修改后重报同一成绩。
- 如继续开发，需说明该集合已被用于开发，并另设评价材料。

本阶段完成条件：
能够用配对结果回答 B2 相对 B1 改善了什么、代价是什么。

## 9. 阶段六：结果复核与结论

### 9.1 复核

- 人工复核主要错误、关键提升和评分争议。
- 条件允许时，由另一位 RA 复核部分案例。
- 报告复核数量和分歧处理方式。
- 隐去系统名称后检查答案，减少预期偏差。

### 9.2 稳定性检查

预先选择一部分题，在 B1、B2 上分别重复运行。
建议各运行 3 次；费用不足时明确说明未完成。

不要只重复成功案例。
不要把裁判之间的分歧当作 Agent 重复运行的方差。

### 9.3 形成结论

可能结论包括：
- 改进有效，值得扩大实验。
- 质量提高，但成本增加过大。
- 只在特定任务上有效。
- 没有稳定增益，假设暂不成立。
- 资源或评价条件不足，尚无法判断。

小样本只支持初步判断。
协议未对齐时，不宣称超过论文或官方排行榜。

## 11. 优先级与交付门槛

P0：
资源核验 → 跑通流程 → 小规模基线 → 失败分析。

P1：
一个改进 → 独立对照 → 人工复核。

P2：
扩大题量、增加模型、对齐官方全量结果。

首次向导师汇报至少包含：
- 资源是否具备。
- 实际完成多少题。
- 基线成绩与成本。
- 主要错误及案例。
- 下一步准备验证什么。

## 12. SUMMARY.md 写作要求

正文控制在约 500—800 字，必要时略超出。
只写结果、证据、限制和下一步，不重复论文背景。
没有完成的项目写“未完成”或“待核验”，不要补写推测结果。
每个重要结论应能链接到配置、结果或案例。
```
