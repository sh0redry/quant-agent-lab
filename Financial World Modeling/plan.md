## 2. 数据选择：先以美股 L3 样本推进，保留加密货币备选

结合你提供的材料，我建议本轮暂定：

> **美股为主，优先使用其他 RA 已经下载的 AAPL、MSFT、Nasdaq 和 NYSE Arca 样本。**

这是实施上的选择：已有样本可以减少采购和接口准备，并能直接检查多场所问题。它不代表已经决定团队长期只研究美股。

| 维度 | 本轮验证 | 后续扩展时再决定 |
|---|---|---|
| 资产 | 优先 AAPL、MSFT | 增加不同流动性、行业的标的 |
| 场所 | 先一个场所，再加入第二个 | 扩展其他重要场所 |
| 时间 | 已有两天样本；先短片段，再完整交易日 | 多周、多月及不同市场状态 |
| 数据 | 原始 MBO／逐订单事件 | 补充参考数据、状态、竞价等 |
| 用途 | 管线正确性、数据覆盖与信息损失分析 | 模型训练、泛化与交互评价 |

**两天、两只股票可以验证管线，不能证明模型具有跨市场状态的泛化能力。**

你提供的价格和覆盖信息先作为采购线索。正式预算需按**具体数据集、日期、标的、许可和使用方式**重新核验，不能直接把某个年费理解成所有资源无条件可用。Databento 当前提供按量与订阅方案，其官方页面也列有历史数据试用额度。[官方定价](https://databento.com/pricing)

加密货币保留为备选，重点核对逐订单原始频道、快照与增量是否完整。**不能拿供应商的 `incremental_book_L2` CSV 当作 L3 替代品**；Tardis 的公开示例中就存在这种 L2 数据类型。[Coinbase 数据说明](https://docs.tardis.dev/historical-data-details/coinbase)

## 3. 阶段一：精读论文，建立“主张—证据—项目影响”清单

这一阶段不是逐段翻译，而是围绕我们需要做的系统读论文。

重点检查：

- **数据：**来源、字段、时间分辨率、资产覆盖与公开范围。
- **处理：**报价与成交对齐、异常与缺失处理、稀疏存储、归一化。
- **模型：**输入组织、编码器、训练目标及增强方式。
- **评价：**预测任务、线性探针、时间划分、横截面及市场状态。
- **边界：**哪些结论针对表示学习，哪些尚不能支持市场模拟和动作影响。

每条重要结论记录：

| 结论 | 论文依据 | 代码依据 | 本地结果 | 对 L3 项目的影响 |
|---|---|---|---|---|
| 示例：某处理模块可以复用 | 页码／章节 | 文件与函数 | 通过／失败／未运行 | 直接用／修改／重写 |

统一使用四类标签：

**论文声明、代码核实、本地实测、我们的建议。**

**阶段产出：**论文能力边界图、数据覆盖表、评价协议表，以及待核验问题清单。

## 4. 阶段二：审查官方资源与代码，确定可复现范围

需要分别检查两个仓库：

- [TFWM](https://github.com/fin-ai-lab/tfwm)：模型、训练、评价及示例。
- [Market-1T](https://github.com/fin-ai-lab/market-1t)：原始行情处理与数据构建。

官方仓库目前说明公开了 2019 年 7 月至 2020 年 12 月的数据子集；完整数据构建另依赖 Massive 原始数据访问。**代码开放与原始数据免费取得是两件事。**[TFWM 资源说明](https://github.com/fin-ai-lab/tfwm)、[数据构建要求](https://github.com/fin-ai-lab/market-1t)

具体操作：

1. 固定论文版本、仓库 commit 和子模块版本。
2. 检查依赖、操作系统、Python、CUDA 和存储要求。
3. 核验数据、权重和结果文件是否实际可下载。
4. 下载前估算文件大小、解压空间及处理成本。
5. 定位数据处理、模型输入、标签生成和评分的实际实现。
6. 对发现的修改单独保存补丁，保留上游原始代码。

重点形成这张表：

| 模块 | 要检查什么 | 对 L3 的预期处理 |
|---|---|---|
| 文件分片、存储与批处理 | 是否与具体字段耦合 | 优先考虑复用 |
| 时间对齐与重采样 | 时间边界、缺失与事件顺序 | 需要按 L3 语义调整 |
| 归一化与样本划分 | 是否只使用历史信息 | 可借鉴，重新验证 |
| 编码器与训练框架 | 输入形状、特征与目标假设 | 需要适配 |
| 原始数据读取 | 是否绑定 Massive 格式 | 新增 L3 数据适配器 |
| 订单生命周期与盘口重建 | 原实现是否覆盖 | 重点新增能力 |
| 动作条件动力学与交互 | 原论文是否实现 | 后续独立开发 |

这些是**待验证的预期分类**，最终需要具体到文件或函数。

## 5. 阶段三：分层完成本地复现，避免把“跑通”当成“复现成功”

先检测本机 CPU、内存、磁盘、GPU 和现有运行环境，再选择实际执行层级。官方说明部分测试与结果重建支持 CPU，训练示例有 GPU 要求。[官方运行说明](https://github.com/fin-ai-lab/tfwm)

| 层级 | 实际执行 | 能得到的证据 |
|---|---|---|
| **R0：环境与官方测试** | 安装依赖、运行相关测试、检查数据与模型导入 | 代码是否能在当前环境运行 |
| **R1：已发布结果重建** | 从作者保存的结果重新生成表格与图 | 结果文件和绘图流程是否一致 |
| **R2：公开数据与权重验证** | 读取真实公开数据，运行编码器和评分流程 | 发布模型是否能实际使用 |
| **R3：单个配置重新训练** | 按公开配方训练，再按相同协议评价 | 在明确子集上的训练复现 |

执行顺序为 **R0 → R1 → R2 → R3**，每层保存命令、配置、耗时、资源和结果。

需要遵守三个区别：

- 从作者结果文件生成图表，属于**结果重建**，没有重新验证模型。
- 小样本推理或少量训练步骤，属于**功能测试**，不能与论文成绩直接比较。
- 正式复现某个公开配置，需要保留其数据范围、横截面、时间划分和评分协议；不能任意缩成几只股票后宣称复现原结果。

**训练优先只选一个有官方端到端示例的配置。** 资源允许再加入一个自监督配置，用来理解方法差异；本轮不默认训练所有模型。

没有合适 GPU 时，继续完成 CPU 测试、代码与数据审查、可执行的推理验证和 L3 实验，并明确记录训练未执行的原因。

## 6. 阶段四：用真实 L3 样本建立最小数据管线

这是本轮最重要的项目落地部分。

计划建立：

```text
原始 L3 文件
    ↓
格式读取与元数据登记
    ↓
事件语义转换、快照初始化与恢复
    ↓
逐订单状态维护
    ↓
L3 订单簿 → L2 深度 → L1 最优报价
    ↓
质量检查
    ↓
事件序列、状态快照与训练样本
```

### 第一步：核实数据身份与完整性

检查：

- 具体数据集、交易场所、标的及时间范围；
- 是否存在订单 ID、事件动作、价格、数量和序列信息；
- 快照、重置、交易状态等记录是否齐全；
- 文件是否已经筛选过，是否影响恢复订单簿；
- 数据是否包含供应商或交易所的质量标记。

Databento 的 MBO 提供订单 ID、订单事件及相关时间字段，适合逐订单状态维护；具体事件语义仍需按文档实现。[MBO 定义](https://databento.com/docs/schemas/mbo)

### 第二步：正确重建订单簿

至少覆盖新增、修改、撤销、成交相关更新、清簿及快照恢复。重点防止：

- 重复扣减成交数量；
- 将不同场所的订单 ID 混在一起；
- 中途读取文件却缺少初始状态；
- 错误处理同一事件的多条记录；
- 将被筛选后的序列跳号直接判断为丢包。

### 第三步：保留三种数据视图

| 视图 | 用途 |
|---|---|
| 原始逐订单事件 | 保留后续订单生成器需要的信息 |
| 重建后的订单簿状态 | 检验盘口、队列及状态转移 |
| L2／L1／固定时间聚合 | 与较粗粒度表示比较，连接 TFWM 思路 |

不要仅保存秒级聚合后删除原始事件，否则会丢失本次最关注的信息。

另外，单个场所重建出来的最优报价，不能直接叫全市场 NBBO；几个场所的合并视图也应明确其覆盖范围。

## 7. 阶段五：完成五组有明确用途的测试

| 测试 | 怎么做 | 希望回答什么 |
|---|---|---|
| **T1：公开资源检查** | 核对数据、权重、配置、依赖和结果 | TFWM 实际可复现到哪一层？ |
| **T2：盘口重建正确性** | 人工可核验的小事件序列＋真实数据回放；有参考盘口时交叉核对 | 我们是否正确理解和处理 L3？ |
| **T3：真实数据质量分析** | 统计异常事件、无效状态、时间问题和恢复情况 | 样本是否适合后续训练？ |
| **T4：粒度与聚合损失** | 将同一段 L3 转成 L2、L1 和秒级视图 | TFWM 类型输入具体遗漏什么？ |
| **T5：多场所适配** | 分别处理两个场所，再检查标的映射和时间对齐 | 一套管线能否支持多场所？还有哪些语义差异？ |

**T4 应成为汇报中的重点图表。** 可以统计：

- 一秒内有多少事件被合并；
- 有多少订单事件发生时最优买卖价没有变化；
- 深度、订单数量、撤单活动及订单存续时间包含哪些额外信息；
- 秒内路径怎样在聚合后消失。

它能支持“粗粒度输入丢失了哪些信息”，但还不能证明“加入这些信息一定提高模型表现”。

若有足够连续日期，再增加一个**探索性模型实验**：在相同时间划分和计算条件下，比较 L1、L2 与 L3 衍生特征对固定预测任务的增量。若只有两天样本，这一步只检查训练流程，不报告泛化优势。

跨场所时间也要单独审查，不能仅将时间戳排序就假定获得了准确的全市场事件顺序。

## 8. 阶段六：把“数据获取方法”转成采购与扩展建议

利用其他 RA 的材料，但逐项补充核验状态。

最终比较表建议包含：

| 比较维度 | 需要记录的内容 |
|---|---|
| 数据覆盖 | 市场、场所、标的、历史起点及中断情况 |
| L3 含义 | 是否有逐订单 ID、事件、快照和恢复机制 |
| 可观察性 | 可见订单的覆盖边界，是否存在截断或缺失 |
| 数据语义 | 不同场所的订单更新和撮合差异 |
| 时间信息 | 时间戳来源、精度、序列及跨场所对齐条件 |
| 取得条件 | 样本、API、历史授权和费用估算 |
| 项目适配 | 与现有样本、代码及后续模型的兼容程度 |

**初步建议采用分阶段扩展：**

1. **当前：**少数美股、单场所、短样本，验证正确性。
2. **随后：**两个场所、更多连续交易日，验证适配与稳定性。
3. **模型研究：**加入更多标的、不同流动性和市场状态。
4. **更广覆盖：**根据模型问题决定是否扩展全市场或其他资产。

不能因为“数据越多越好”就直接确定四年全市场采购。所需时间与资产规模，应由后续训练目标、泛化问题和小样本测得的资源成本决定。

## 10. 执行顺序与结束条件

| 顺序 | 工作 | 结束条件 |
|---|---|---|
| 1 | 检查本机、现有样本和官方资源 | 明确可以运行什么、需要什么资源 |
| 2 | 论文与代码审查 | 重要结论都有可追溯依据 |

| 5 | 信息损失及多场所分析 | 得到可以放进汇报的图表与结论 |
| 6 | 汇总 Markdown | 正文可独立阅读，结果能追溯到配置与日志 |

按资料齐备、样本可用的情况，**论文审查、CPU 验证与 L3 小样本分析可以按数个工作日组织**；训练和正式公开协议评价的耗时，需要先测下载量、GPU 和运行速度再估算。

这一轮最终应给教授一个具体判断：

> **TFWM 值得复用哪些方法和代码；公开部分验证到了什么程度；我们的 L3 数据管线已经跑通什么；下一阶段还需要哪批数据、多少资源，以及怎样验证它们的价值。**
